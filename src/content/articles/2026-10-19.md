## Codexをブラウザーから操作するOriel

[Oriel](https://github.com/mikan-919/oriel)は、手元で動くCodexをブラウザーから操作し、GitHub IssueとLinearを使って開発を進めるツールだ。10月15日に、利用端末で動くデーモン[orield](https://crates.io/crates/orield)の0.1.0をcrates.ioへ公開した。

構成は3つに分かれる。

```text
ブラウザー ── Oriel Web ── Relay（Cloudflare）── GitHub / Linear
                              │
                              └─ orield（手元）── Codex
```

`orield`は手元の端末でCodexを起動し、WebSocketでRelayへつなぐ。Relayは認証、端末とブラウザーの通信、GitHubとLinearの連携を担当する。Oriel Webはブラウザー側の画面だ。

`orield workflow`は、GitHub Issueの要求（WHAT）からLinearに実装計画（HOW）を作る。計画の作成は読み取り専用で、コードを変更するには、人がLinearのTodoで承認することと、対象リポジトリの`.oriel.yaml`で実行を許可することが必要になる。承認後の実装はCodexの`auto_review`で実行要求を審査する。

インストールは次の通り。

```sh
cargo install orield --locked --version '=0.1.0'
```

公開と同時に、境界の不具合も直していた。端末中継は、ブラウザーの接続ごとにセッション、端末、有効期限を持つ許可を発行し、転送するフレームごとに認証する。ログアウト時はセッションを削除し、接続中の端末へ失効を通知する。通知に失敗した場合はセッションの削除だけを確定し、再試行できるようにした。

ほかに、JSON要求の上限を本文全体の読み込み前に適用する、同名のGitHub検査を別の検査として扱う、停止要求でCodexの子プロセスを終了する、強制終了後に検証用の子プロセスが残らないようにする、といった修正が入っている。機能を増やすより、実行を止める条件と認証の境界を詰めた期間だった。

## Cloudflareの無料枠で止まった

Orielを常時動かしていたところ、Durable Objectsの無料枠で本番が止まった。表示されたのは`Exceeded allowed rows read in Durable Objects free tier.`というエラーだった。リクエスト数ではなく、SQLの読み取り行数が上限を超えていた。

旧実装は、待機中も15分ごと、実行中は約5秒ごとにGitHubとLinearを照合していた。48件のIssue、1件のHOW、PRなしという同じデータで測ると、全件探索はHTTPで967行、WebSocketで1,542行、実行中の1件確認は326行だった。実行中の確認を全件探索から対象Issueの取得へ変えると、HTTPの全件探索に対して読み取りは約66%減る。

待機中の全件照合は、GitHubとLinearの両方のWebhook署名キーを設定した場合は15分ごとにした。60秒ごとの1,440回から96回へ減る。Webの一覧は通知を受けたときに更新する。

| 処理 | 読み取り行数 |
| --- | ---: |
| 全件探索（HTTP） | 967 |
| 全件探索（WebSocket） | 1,542 |
| 実行中の1件確認 | 326 |

ただし、5秒ごとの確認を24時間続けると、326行でも1日約563万行になる。無料枠は500万行なので、これだけでは24時間の連続実行を保証できない。周期を伸ばすだけでは足りず、実行中の確認から認証の読み取りを外すか、取得そのものを通常のWorkerへ移す必要がある。この見積もりと削減案は`CLOUDFLARE_COST.md`に残した。

## Irisoutの一覧更新をVanillaと比べた

[Irisout](https://github.com/mikan-919/irisout)は、JSXから静的HTMLとDOM更新処理を生成するコンパイラだ。10月8日に0.3.7をnpmへ公開した。

10月は一覧の更新速度を測っていた。js-framework-benchmarkのIrisout実装を追加し、行の作成、追加、削除、交換、部分更新、全削除の9操作を、手書きのVanilla JavaScriptと比較した。

R1からR7までの改善で、1,000行の作成は3.1750msから2.9175ms、10,000行の作成は31.3000msから29.1925ms、交換は0.0581msから0.0108ms、削除は0.2150msから0.1425msになった。同期比較の95%区間が0を含まないものだけを改善として扱っている。

| 操作 | 修正前 | 修正後 |
| --- | ---: | ---: |
| 1,000行作成 | 3.1750ms | 2.9175ms |
| 10,000行作成 | 31.3000ms | 29.1925ms |
| 交換 | 0.0581ms | 0.0108ms |
| 削除 | 0.2150ms | 0.1425ms |

一方で、全操作でVanilla以下という目標には届いていない。生成するJavaScriptのBrotli転送量は4.7KiBで、Vanillaは2.5KiBだった。1,000行作成後のメモリは2.134MiBで、Vanillaは1.879MiBだった。速くなった操作はあるが、生成コードの大きさと初期化の費用は残っている。

改善の採否も決めた。通知と固定位置交換の最適化は、修正前後の差が95%区間で確定せず、生成JavaScriptが384バイト、gzipで112バイト増えた。このため採用を保留し、既存コードは撤去していない。差が確認できない最適化を積み増さない基準を`docs/project-direction.md`に置いた。

## 公開文書だけでアプリを作らせた

10月19日に、変更ごとのブラウザー検査をCIへ接続した。`bun run test:browser`で、保存済みのハンドラー8項目、初期化と破棄8項目、関数境界のmountとhydrate、障害対応ボード8項目を実行する。公開物の構築、別ディレクトリへの導入、型検査、本番構築、空きポートでの起動と停止までを1コマンドで行う。全606試験、静的検査、実例と公式サイトの構築を通過した。GitHub Actionsでの遠隔実行はまだ確認していない。

検査は、公開版0.3.7と公開文書だけを読んだ実装役にも試してもらった。障害対応ボードを3回の型検査と本番構築で完成させ、既存8項目と追加8項目の操作が成功した。ブラウザーの例外は0件だった。

この試用で、いくつか不具合が見つかった。要素の間の静的な文字列式`{' '}`を反応的な本文と判定して、一覧の構築を拒否する制約があった。`<main><span>before</span>{" "}<span>after</span></main>`のような最小例で再現し、静的な文字列を初期HTMLへ書き出す処理へ分けた。Layoutのpropsと親のsignalが同じ名前だと`title()()`になる問題、子ルーターに`onError`を追加すると経路を検出できなくなる問題も直した。

いずれもmainブランチの修正で、npm公開版0.3.7は変更していない。公開版を使った当時の記録は残し、修正版の公開は次に行う。

## LogosとZestium

[Logos](https://github.com/mikan-919/logos)は、複数のアプリが同じEntityへComponentを追加して情報を共有する基盤だ。TagMemoはメモとタグを扱う画面、Zestiumは本人の記録、願望、つながりを保存して見返す画面になる。同じEntityを別のアプリが別のComponentで拡張できるため、アプリごとに同じデータを複製しなくてよい。

Logos Workerの`/mcp`はHTTPのMCP接続先で、EntityとComponentの取得、作成、更新、削除を公開している。Better Authのセッションを使うため、MCPクライアントにはログイン時のCookieを設定する。セッションがない要求は401を返す。

Zestiumでは、投稿、願望、投票、つながりをLogosへ保存する。同じ願望が複数の投稿に現れても一つのEntityとして扱い、投稿と願望の間に相互参照を張る。手動投票は日本時間の同日一回までで、願望を別の日に三回表示して投票がなければ一覧から外す。

10月5日には、実際のBetter Authとメモリー内のデータベースを通す受け入れ試験、VLMKitによる画面の欠落・はみ出し・画面幅の検査、Lucideアイコンへの統一まで行った。

## 小さな実験

Hibanaは、マクロ構文を検証するためのPEGパーサだ。Rustで依存クレートなしに書き、`syntax`と`macro`の宣言を読みながら、その場で文法を拡張する。ラベル、繰り返し、選択、`prec`によるPratt法の優先順位、`where`による原文の一致検査、`lexer raw`、テンプレート展開を扱う。衛生的な展開、メモ化、構文木の型生成はまだない。最悪ケースは指数時間になる。

Anifestaは、Bevy 0.20でブルドーザーのブレードが浅い土層を押し出す様子を作る試作だ。2.5次元の有限体積モデルで、MPMやDEMの土質シミュレーターではない。砂、ローム、粘土で粘着力、摩擦、圧密、堆積の係数を変え、質量保存と圧密の試験を付けている。こちらは作業中で、公開できる段階ではない。
